## Query plans and tuning

`npm run bench:explain` captured `EXPLAIN (ANALYZE, BUFFERS)` for every statement of every read
endpoint (the service code itself, 5 draws per kind):
[ten-year](data/2026-10-26-baseline-ten-year-explain.md),
[stress](data/2026-10-26-baseline-stress-explain.md). Database time per request, slowest kinds:

| Request kind                           | Ten-year median / max ms | Stress median / max ms |
| -------------------------------------- | -----------------------: | ---------------------: |
| inventory: search two words            |                3.8 / 4.1 |          111.3 / 232.1 |
| inventory: search ID fragment          |              11.7 / 16.2 |            59.2 / 80.1 |
| inventory: search test hole            |               3.5 / 10.3 |            12.2 / 86.0 |
| inventory: search one common word      |                3.3 / 4.0 |            21.2 / 27.8 |
| inventory: filter type + status        |                2.0 / 2.3 |             9.5 / 12.1 |
| inventory: default view                |                1.3 / 1.7 |              5.4 / 5.6 |
| lookup, detail, history, print history |                   <= 0.2 |                 <= 0.2 |

**What the plans show.** Lookups, detail, history and print history use indexes throughout
(`storage_unit_readable_id_key`, `audit_event_entity_idx`, `print_job_item_unit_idx`, primary
keys); the only sequential scans are of the small `location` and `app_user` tables. Every slow
case is the inventory **page** query for a search: with `ORDER BY received_date DESC … LIMIT 25`,
the planner walks `storage_unit_received_date_idx` backwards and checks each unit's search document
(`storage_unit_search_pkey` lookups), expecting to find 25 matches early. For words that match
few, older units (e.g. "tamarack hill": 840 matches) it reads ~40,000 units first (165,961 buffer
hits, 219 ms). The count query for the same search uses the trigram index and takes 12 ms.

**Candidate tried: fence the search** (find matching documents through the trigram index first,
`OFFSET 0` subquery, then sort). Measured on the stress data (best of 4, page query only):

| Search        | Matches | Current ms | Fenced ms |
| ------------- | ------: | ---------: | --------: |
| tamarack hill |     860 |       85.8 |      11.3 |
| th19-03       |     774 |       46.3 |      10.3 |
| bh17-01       |   2,347 |       67.6 |      29.1 |
| creek         |   9,678 |        1.3 |      27.8 |
| cedar         |   7,869 |        1.4 |      27.2 |
| sample        |  15,087 |        0.3 |      29.3 |

It caps the worst case near 30 ms but makes every common-word search about 20x slower, because it
must join and sort all matches. No index can serve this shape: the filter is on
`storage_unit_search`, the sort on `storage_unit`.

**Decision: no index or query change.** Every target is met with a wide margin at ten-year volume
and at 5x stress (inventory p95 83 ms against 500 ms; worst single inventory request 151 ms), so the tuning
rule "measured benefit" is not satisfied for any candidate: the fence trades one slow minority for
a slower majority, and the remaining costs (counts over current stock, 5-10 ms at stress) are far
below what users would notice. The reserved migration `0017` is not used. Receipt-write overhead is
therefore unchanged (37 ms p95 ten-year, 56 ms stress, 5 units per receipt).

If the host misses the inventory target, the first lever is the fence above (or storing
`received_date` / `readable_id` beside the search document so one index serves both), measured
again on the host.

## Caveats

- Dev PC, much faster than a typical office PC; the host will be slower. AC2 stays open until the
  host run.
- The load generator ran on the same PC as the API and PostgreSQL (as it will on the host), over
  HTTP on 127.0.0.1; production adds TLS.
- AVG Web Shield was on. Results were steady between runs, so no stall was seen, but it may affect
  local traffic on a machine that has it.
- autocannon paces in whole requests per second, so the workload is heavier than agreed (scanners
  every 1 s, not 3 s; every user a page per second).
- Data is generated, not real: real search text may be more or less selective than the invented
  vocabulary.
